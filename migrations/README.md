# Версии схемы АТЛАС

Миграции выполняются `app.db.migrate_database()` в транзакции с блокировкой БД. Это небольшой явно версионируемый мигратор конкурсного прототипа; он работает с SQLite и PostgreSQL. Команда: `python -m app.db migrate`. Исполненный revision хранится в таблице `schema_migrations`.

- Исходная версия: users, login_sessions, lessons, lesson_changes, grades, deadlines, document_requests, notifications.
- `0002_workflow` (06.11.2026): additive columns document_requests.staff_message/version/due_at, notifications.target/request_id; новые request_events, request_idempotency, login_attempts, schema_migrations; индексы сессий и списков. Данные не удаляются. Для существующих заявок срок рассчитывается из сохранённой даты; история помечается как перенесённая и не изобретает отсутствовавшие этапы.
- `0003_listing_indexes` (06.11.2026): индексы заявок status/created_at/id и due_at/status, уведомлений student_id/is_read/created_at для серверных фильтров и страниц. Поля и данные не меняются. Счётчики, фильтр и строки ответа читаются в одном snapshot; optimistic compare-and-swap статусов остаётся атомарной отдельной write-транзакцией.
- `0004_full_campus` (07.11.2026): дополнительные таблицы учебного контура, консультаций, переписки, мероприятий, библиотеки, финансовых демозаписей, предпочтений и портфолио. Существующие таблицы и записи не очищаются. Модели расширений регистрируются в общей metadata до `create_all`. В CLI `python -m app.db` используется тот же реестр моделей, что и при запуске сервера; это проверено отдельным subprocess-тестом.
- `0005_contest_hardening` (09.11.2026): личные черновики `personal_drafts`, квоты `write_quotas`, квитанции уточнений `request_followup_receipts` и безопасных повторов `service_idempotency`. Уточнение повышает версию заявки, но не меняет её статус. Существующие записи не очищаются.
- `0006_audit_integrity` (10.11.2026, приложение 3.2.1): добавляет случайный неизменяемый `record_token` к конспектам, личным задачам, карточкам, фокус-сессиям и портфолио. Все ID, владельцы и содержимое сохраняются; поле заполняется и получает уникальный индекс. Для новых вставок имеются Python default и резервный SQL default/SQLite trigger. Условные UPDATE/DELETE проверяют одновременно ID, владельца и токен, в том числе при повторном использовании SQLite integer ID.

Revision 0006 оставляет старые черновики `note:N`, `task:N`, `flashcard:N`, `focus:N`, `portfolio:N` с исходными именами и содержимым. Один номер не доказывает принадлежность нынешней записи: он мог быть повторно использован ещё до обновления. Поэтому такие черновики доступны для явного восстановления через личный экспорт `GET /api/drafts/export` (`requires_manual_recovery:true`, `legacy_recovery_count`), но не подставляются автоматически в новую запись. Новые формы используют `kind:N:record_token`.

Квитанции, повторявшие растущую историю заявок или переписку, заменяются компактными ссылками на неизменяемые строки истории: исходная сводка, максимальный ID дочерней строки, размер и начало захваченной страницы. Это не удаляет историю и не изменяет сохранённый ответ при повторе, включая старые ответы длиннее 100 событий. Преобразование допускается только после проверки полного совпадения дочерних строк и захваченной страницы; неподтверждённые старые JSON сохраняются целиком. Старые квитанции повторения карточек не привязываются к новому токену: API умеет возвращать их прежний результат без повторной записи попытки.

Сроки старых заявок исправляются только когда `due_at` в точности совпадает с прежним расчётом от UTC-даты и отличается от расчёта от московского дня создания. Произвольно изменённый иной срок не заменяется. Новые и повторно перенесённые заявки используют московский день.

`seed_learning(db)` выполняется однократно на известного демостудента по маркеру; повторный startup не воссоздаёт удалённые личные задачи и не сбрасывает прогресс. `seed_services(db)` использует устойчивые ключи каталога, не сбрасывает счётчики мест и книг, переписку или настройки. Оба seed вызываются под общей блокировкой и только в DEMO_MODE. Входы и прежние заявки сохраняются. Перед первым локальным обновлением версии 3 создана штатная SQLite backup; сравнение исходных значений восьми таблиц дало PASS: `docs/verification/extension-preservation-report.json`.

Новая пустая БД создаётся сразу с актуальной схемой; демоданные добавляет отдельный seed в lifespan только при DEMO_MODE=true. Повторное выполнение migration не дублирует историю. Совместимость и сохранение исходной заявки/уведомления проверяет `tests/test_workflows.py` на созданной в тесте базе предыдущей версии.

Следующие изменения схемы должны иметь новую revision, отдельную проверку существующей БД и процедуру резервного копирования. Не редактировать уже выполненный revision для разрушительных операций и не удалять atlas.db для применения обновления.

Перед развёртыванием 3.2.1 сделайте и проверьте штатную резервную копию. На целевой БД с прежними настройками `DATABASE_URL` выполните `python -m app.db migrate` до приёма запросов новой версией; повторный запуск безопасен. Обновляйте все workers вместе: старый код без токенов не защищает от замены записей. Не откатывайте схему удалением таблиц/колонок; при необходимом полном откате используйте проверенную резервную копию и соответствующий ей выпуск. Во время исправлений рабочая `atlas.db` проекта не мигрировалась; SQLite и PostgreSQL-проверки выполняются на отдельных тестовых базах. См. [актуальную приёмку](../docs/release-checklist.md).
