# Конкурсная база осени 2026

Набор `autumn-2026` моделирует работу АТЛАС с 1 сентября по 22 ноября 2026 года, 12:00 МСК. Конкурсная проверка проходит с 23 ноября, 00:00, по 28 ноября, 23:59, включительно по Москве. Люди, учебные результаты, финансовые операции и делопроизводство синтетические. Вход и кабинеты показывают действующую маркировку конкурсного концепта.

## Инициализация и повторный запуск

Команда использует явно заданный `DATABASE_URL` и `DEMO_MODE=true`. Проверьте, что URL указывает на выделенную пустую БД. Пример для новой локальной SQLite.

```powershell
$contestDatabase = Join-Path $env:TEMP ('atlas-contest-' + [Guid]::NewGuid().ToString('n') + '.db')
$env:DATABASE_URL = 'sqlite:///' + ($contestDatabase -replace '\\','/')
$env:APP_ENV = 'development'
$env:DEMO_MODE = 'true'
.venv/Scripts/python.exe -m app.contest
.venv/Scripts/python.exe -m uvicorn app.main:app
```

Команда проверяет отсутствие таблиц, применяет миграции и заполняет набор в одной транзакции. Существующая БД с таблицами получает отказ до миграций. Журнал `schema_migrations` и поле `contest_datasets.initialized_at` отражают реальное время установки. Записи о смоделированных действиях имеют собственные даты. Повторный запуск на БД с этим набором возвращает `already_initialized` и текущие количества строк. При ошибке транзакция откатывается. Для чистого повтора создайте новую БД с другим именем.

Миграция `0025_contest_dataset` добавляет только таблицу-маркер. Занятия, отметки, попытки, отзывы, суммы, подборка документов и кампании используют действующие таблицы и API. В `app/contest` академический генератор строит группы, нагрузки, календарь и задания. Кампусный генератор добавляет связанные сервисы. Подразделения используют собственную историю и публикации. Идентификаторы и исторические связи воспроизводимы. Время установки, соли хешей паролей и случайные значения шифрования рассчитываются при запуске.

## Баллы и даты проверки

Ведомость начинается с нуля. Баллы появляются за проведённый разбор с отметкой посещаемости либо за принятую попытку с выставленным баллом. Запись хранит преподавателя, дату, дисциплину, занятие и при наличии результат проверки работы. Корректировка одного результата добавляет балл после повторной сверки критерия и сохраняет исходные сведения. Генератор сверяет каждую ведомость с суммой начислений и поправок перед фиксацией.

В начале недели в кабинетах есть ближайшие пары, открытые задания, обращения на рассмотрении и записи на мероприятия. Задания, назначенные к публикации 25 ноября, становятся видимыми по штатному правилу. Задания и консультации на начало декабря сохраняют актуальность в конце 28 ноября. Субботний практикум виден как запланированное занятие. У будущих занятий отсутствуют отметки, работы без проверки отсутствуют в журнале баллов, а оценки за аттестацию после 22 ноября остаются открытыми.

## Переключение публичного стенда

Выполняйте переключение в плановое окно после проверки назначения `atlas`, разрешения на замену публичного набора, отсутствия смешанных данных и учёта служебных аккаунтов. При наличии пользовательских или важных служебных данных используйте отдельный конкурсный стенд. Старые БД и тома сохраняются. Используйте учётную запись администратора PostgreSQL и обычную конфигурацию сервера. [Развёртывание и переменные окружения](deployment.md).

1. Соберите образ для выпуска. Запишите прежний рабочий коммит и тег образа. Проверьте `DEMO_MODE` и имя БД через действующее приложение. Держите служебные пароли в закрытой конфигурации.
2. Сделайте резервную копию действующей базы штатным скриптом и проверьте архив и контрольную сумму. Восстановите дамп командой `scripts/restore.sh ПУТЬ_К_ДАМПУ atlas_restore_20261122` в свободное имя и сравните количество заявок, основные справочники и журнал миграций с исходной БД. История проверки справок входит в резервную копию. Штатные дампы исключают закрытые вложения и пояснения. Сохраните исходную БД для отката с сохранением всех записей. [Резервное копирование и восстановление](deployment.md).
3. Подготовьте отдельную PostgreSQL БД и запустите генератор в контейнере нового образа. Проверьте отчёт и повтором подтвердите `already_initialized`.

   ```sh
   docker compose exec -T db createdb -U atlas_admin -O atlas_app atlas_contest_2026
   docker compose run --rm --no-deps web sh -c 'DATABASE_URL="${DATABASE_URL%/*}/atlas_contest_2026"; export DATABASE_URL; exec python -m app.contest'
   ```

4. Перед переключением остановите таймеры мониторинга и бэкапа. Остановите web, дождитесь закрытия его подключений и сделайте заключительный дамп. После проверки свободных имён переименуйте обе БД в одной транзакции из базы обслуживания `postgres`.

   ```sh
   docker compose exec -T db psql -U atlas_admin -d postgres -v ON_ERROR_STOP=1 <<'SQL'
   BEGIN;
   ALTER DATABASE atlas RENAME TO atlas_pre_contest_20261122;
   ALTER DATABASE atlas_contest_2026 RENAME TO atlas;
   COMMIT;
   SQL
   ```

5. Запустите web из нового образа. Проверьте маркер `autumn-2026` в `atlas`, `/api/health`, `/api/ready`, TLS, баллы с датами и заданиями в кабинете Алины, отдельную историю Марка, очередь учебного офиса и открытые сроки. Запустите таймеры и проверьте следующий бэкап.
6. Для отката остановите web. Из `postgres` в одной транзакции верните новой базе имя `atlas_contest_2026`, затем прежней верните имя `atlas`. Поднимите прежний образ и проверьте готовность и восстановление таймеров.

PostgreSQL требует выполнять переименование из другой БД кластера. Штатные бэкап, мониторинг и конфигурация приложения используют стабильное имя `atlas`. [Документация PostgreSQL 17](https://www.postgresql.org/docs/17/sql-alterdatabase.html).
