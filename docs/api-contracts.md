# Контракты API АТЛАС

Контракты ядра локального конкурсного концепта с дополнениями до 3.5.0,
11 ноября 2026 года. [Учебное расширение](learning-api.md), [сервисы](services-api.md),
[преподаватель и административные операции](academic-workspace.md),
[профсоюз и ВУЦ](union-vuc-implementation.md). Все данные и учётные записи
вымышлены. Формат дат ISO 8601. Моменты времени нормализуются в UTC (`+00:00`),
учебные дни и время занятий используют `Europe/Moscow` (UTC+03:00).

## Доступ и ошибки

- Сессия: `atlas_session`, HttpOnly / SameSite=Lax; Secure в HTTPS. В БД только SHA-256 токена, пароль Argon2id. Сессия действует 7 дней; при входе очищаются истёкшие и сохраняется не более 20 активных сессий аккаунта.
- Все POST требуют `X-Requested-With: ATLAS`. Присутствующий Origin должен совпасть с `PUBLIC_ORIGIN`, локально — с origin запроса. Cross-site и same-site `Sec-Fetch-Site` отклоняются. CORS не разрешён.
- Все тела имеют `extra=forbid`: нельзя прислать `student_id`, `role`, `status` в форму новой заявки. Владелец присваивается исключительно сервером из сессии.
- Чужие ресурсы студента: 404. Чужая роль: 403. Без сессии: 401. Неверные поля: 422. Конфликт версии/статуса/повторной отправки: 409. Ограничение входа: 429 с `Retry-After`. Размер фактического тела, включая chunked: до 32 KiB, иначе 413.
- Неуспешные входы сохраняются в БД на 15 минут: до 12 попыток на IP+логин и 40 на IP. Проверка сериализована SQL-блокировкой, действует между процессами. Неизвестный логин всё равно проходит Argon2-проверку фиктивного хеша. В ответах нет паролей, токенов или внутренних ошибок БД.
- API отдаёт `Cache-Control: no-store, private`; CSP, nosniff, frame denial, referrer policy применяются также к ошибкам.
- Аутентифицированный клиент отправляет `X-ATLAS-User` со своим ID, захваченным до начала запроса. Если общая cookie уже переключена на другой аккаунт в соседней вкладке, сервер возвращает 409 `{detail:{code:'account_changed',message}}` до чтения личных данных/списания квоты/изменения ресурса. Неверный формат — 422. Заголовок не назначает владельца, а только сверяется с сессией; его отсутствие поддерживается для прежних клиентов. Защита действует и при logout. Клиент дополнительно синхронизирует смену аккаунта между вкладками.
- Проверки Argon2 ограничены двумя одновременно: PostgreSQL advisory transaction locks действуют на все workers, локальный SQLite использует ограничитель процесса. Избыточный вход — 429 `Retry-After: 1`; это дополнение к сохранённым ограничениям перебора. Сроки сессий сравниваются как UTC-моменты независимо от timezone соединения PostgreSQL.

## Пагинация, поиск и точные счётчики

8 ноября по запросу пользователя удалён помощник «Подскажет АТЛАС» вместе с серверной функцией. `/api/navigator` больше не зарегистрирован и возвращает 404 для всех ролей и без сессии. Расписание, оценки, заявки, справочник и обычный поиск остаются самостоятельными сценариями.

GET `/api/requests`, `/api/staff/requests`, `/api/notifications` поддерживают `paginated=true&offset=0&limit=30&filter=all&q=...`.

```json
{"items":[],"total":211,"offset":0,"limit":30,"has_more":true,"counts":{"all":211,"active":1,"submitted":1,"review":0,"processing":0,"needs_info":0,"ready":105,"rejected":105,"overdue":1}}
```

`items` здесь показан схематично; фактическая страница содержит до limit записей. `total` учитывает текущие поиск и фильтр, `counts` описывает все доступные пользователю записи независимо от фильтра/поиска. При смене фильтра или запроса UI сбрасывает offset. Параметры: offset от 0 до 2147483647, limit от 1 до 200 (совместимый default 200), q до 100 символов. Неверные значения/управляющие символы возвращают 422. Ключи фильтрации заявок: all/active/overdue/submitted/review/processing/needs_info/ready/rejected; overdue — незакрытые заявки с due_at раньше текущего учебного дня. Active включает submitted, review, processing и needs_info. Закрытые заявки не скрывают старую активную, поскольку фильтр применяется до LIMIT.

Поиск заявок: тип, комментарий, номер (`42`, `#42`, `№42`), дополнительно для сотрудника — имя и группа. Поиск уведомлений: заголовок и текст. Поиск нечувствителен к регистру кириллицы и латиницы; `%`/`_` трактуются буквально. Уведомления: filter all/unread/schedule/deadline/request/announcement, counts `{all,unread,schedule,deadline,request,announcement}`; отдельное поле `unread_count` показывает точное число непрочитанных во всём аккаунте, даже когда оно больше страницы.

Без `paginated=true` сохраняется совместимый массив с теми же offset/limit/filter/q. Все ответы списков имеют `X-Total-Count`, уведомления также `X-Unread-Count`. Порядок стабилен: created_at DESC,id DESC. Чтение не изменяет записи или read-флаги. Данные страницы, total и counts читаются в одной snapshot-транзакции: PostgreSQL REPEATABLE READ / READ ONLY, SQLite BEGIN; конкурентная смена статуса не смешивает две версии счётчиков в одном ответе. При изменениях между страницами пользователь обновляет список; offset не является неизменяемой архивной выборкой.

`next_lesson` — текущая ещё не закончившаяся или следующая пара в текущей/следующей неделе, по московскому времени. `open_requests` исключает ready и rejected. Незавершённые просроченные дедлайны остаются видимыми.

## Жизненный цикл заявки

Новая заявка возвращает 201. `comment` для обращения и услуг с `requires_comment:true` после trim минимум 10 символов. Неизвестный ключ услуги возвращает 422. Группы услуг и фактические названия: [каталог](features.md). Необязательный `Idempotency-Key`: 8–100 символов `[A-Za-z0-9_-]`; клиент генерирует UUID на одну отправку. Повтор того же ключа и нормализованного тела возвращает прежнюю заявку с 200 без дубликатов событий и уведомлений. То же значение с другим телом → 409. Ключи разных студентов независимы; уникальность гарантирована SQL constraint.

Сводка заявки:

```json
{"id":42,"type":"Справка об обучении","comment":"Для демонстрации","status":"review","created_at":"2026-11-06T09:00:00+00:00","updated_at":"2026-11-06T09:05:00+00:00","version":2,"staff_message":"Заявка принята","due_at":"2026-11-10","document_url":null}
```

`due_at` — ориентировочный срок 2/3/5 рабочих дней по типу заявки, без учёта региональных праздничных дней; это не обещание реальной службы. `document_url` есть только для ready. Документ явно помечен «КОНКУРСНЫЙ ОБРАЗЕЦ / ВСЕ ДАННЫЕ ВЫМЫШЛЕНЫ», не имеет юридической силы, подписи и печати. Выписка содержит только оценки владельца. Справка о стипендии честно сообщает, что суммы демонстрационной финансовой ленты не подтверждают реальное начисление или выплату.

Детали дополнительно содержат:

```json
{"history":[{"id":11,"status":"submitted","message":"Заявка принята и передана в учебный офис.","actor_role":"student","actor_name":"Алина Ветрова","created_at":"2026-11-06T09:00:00+00:00"}]}
```

## API сотрудника

| Метод / путь | Контракт |
|---|---|
| GET `/api/staff/requests` | сводки всех вымышленных заявок + `student_name,group` |
| GET `/api/staff/requests/{id}` | детали + история + `student_name,group` |
| POST `/api/staff/requests/{id}/status` | `{status,message?:string<=2000,expected_version?:int>=1}` → обновлённые детали |

Разрешённые переходы: submitted → review/needs_info/rejected; review → processing/needs_info/ready/rejected; processing → needs_info/ready/rejected; needs_info → review/rejected. Финальные ready/rejected изменить нельзя. Для ready, rejected и needs_info ответ/причина после trim минимум 10 символов. Версия повышается на каждом переходе; UI всегда отправляет `expected_version`. Сервер выполняет атомарный compare-and-swap, предотвращая одновременную перезапись. Для старых клиентов поле допускается без значения, но SQL-гонка всё равно даёт 409 одному из конкурирующих обновлений. Статус, событие и уведомление записываются одной транзакцией. Сотруднику запрещены студенческие оценки, расписание, документы и личные endpoints.

## Миграции и запуск

Импорт `app.main` не создаёт и не заполняет БД. FastAPI lifespan вызывает `initialize_database()`: проверка окружения → аддитивные migration до `0006_audit_integrity` → seed только в DEMO_MODE и только пустой таблицы пользователей. Полный реестр и порядок обновления: [миграции](../migrations/README.md). SQL-блокировка SQLite BEGIN IMMEDIATE / PostgreSQL advisory transaction lock защищает запуск нескольких workers. Существующие заявки, пользователи и уведомления сохраняются. История старой заявки содержит только известный текущий статус и честную системную запись; ранние переходы не выдумываются.

```text
python -m app.db migrate
python -m app.db seed
```

Production требует PostgreSQL, HTTPS PUBLIC_ORIGIN без пути, Secure cookie, явный ALLOWED_HOSTS без wildcard, отдельного пользователя БД и случайного пароля не короче 32 символов после URL-декодирования. Шаблонные пароли отвергаются. Миграции аддитивны; откат приложения не удаляет новые таблицы. Перед обновлением нужен проверенный backup; фактические deployment/restore проверки описаны отдельно в release-документации.

## Уточнения 3.2.1, 10 ноября 2026

GET `/api/requests/{id}` и `/api/staff/requests/{id}` принимают `history_limit` 1–200 (default 100) и необязательный `history_offset` 0–2147483647. Ответ содержит `history`, `history_total`, `history_limit`, `history_offset`, `history_has_more`. Без offset возвращается последняя выровненная страница: `max(0,(total-1)//limit*limit)`, внутри страницы события идут хронологически по `created_at,id`. Явный offset 0 возвращает начало; вся история доступна последовательными страницами. Отправка уточнения сохраняет точную прежнюю версию и допустимый текущий статус в одном SQL-условии; предсказанная следующая версия не обходит финальное состояние.

Квитанции уточнений/переписки хранят сводку и границу неизменяемой истории вместо повторения её текста в каждом JSON. Повтор возвращает захваченную исходную страницу, даже когда новые события уже появились. Старые полные ответы сохраняют свой исходный размер и поля при повторе; неверифицируемые старые снимки не удаляются. Успешный повтор создания с уже сохранённым ключом проверяется до динамического ограничения даты: начавшаяся консультация, мероприятие или наступившая желаемая дата пересдачи не превращает ранее завершённый запрос в ошибку. Новая отправка с иным ключом проходит обычную проверку будущей даты.

Конспекты, личные задачи, карточки, фокус-сессии и портфолио возвращают `record_token` (32 hex). При изменении, повторении и удалении существующей записи новый клиент передаёт `X-ATLAS-Record`. Неверный формат даёт 422, несовпадение — 409 `record_changed`. Заголовок необязателен для старых клиентов, но SQL всегда проверяет ID + владельца + токен прочитанной записи, поэтому отложенная операция не меняет запись другого студента после повторного использования ID. Новые черновики редактирования используют `kind:id:record_token`; GET/PUT такого имени проверяет текущую запись. Создание остаётся под прежними именами форм.

GET `/api/drafts/export` возвращает только собственные `{items:[{name,values,updated_at,requires_manual_recovery}],legacy_recovery_count}`. Старые имена `kind:id` сохраняются без автоматической привязки к существующему ID и отмечены для явного восстановления. Экспорт не включает чужие черновики и не исполняет их содержимое. Клиент читает сохранённый ключ отправки до новой отправки, считает SHA-256 нормализованного тела и обязательно подтверждает durable PUT ключа перед основным POST. Ошибка чтения/PUT останавливает основной POST; повтор после потерянного ответа использует тот же сохранённый ключ.

Лимиты создания личных записей (200, фокус/попытки 1000) проверяются вместе с INSERT под блокировкой владельца. Старые записи сверх лимита не удаляются и остаются доступны в списках. Портфолио поддерживает тот же `Idempotency-Key` и конфликт другого тела 409. Целочисленные варианты пути (`+1`, `01`, пробел) нормализуются перед классификацией квот тем же правилом, что использует API.

## Объявления учебного офиса

- `GET /api/announcements` возвращает доступные пользователю опубликованные объявления, при `status=archived` — архив ранее опубликованных. Фильтры `category`, `priority`, `q`, `sort=featured|newest|oldest` и `offset` применяются до `limit` (1–50). Страница содержит `items`, `offset`, `limit`, `more`. `GET /api/announcements/{id}` возвращает полный текст или 404 вне аудитории и для черновика.
- `GET /api/staff/announcements` и `GET /api/staff/announcements/{id}` доступны только учебному офису. В списке также есть черновики. Карточка включает историю изменений страницами по 20 записей (`history_offset`, `revision_offset`, `more_revisions`). Допустимые учебные группы перечисляет `GET /api/staff/announcements/groups`.
- `POST /api/staff/announcements` создаёт черновик (`status=draft`) или публикует сразу (`status=published`). `PATCH /api/staff/announcements/{id}` редактирует запись, публикует, снимает с публикации (`draft`) или архивирует её (`archived`). Архив доступен для чтения. `version` обязателен при изменении, конфликт версий возвращает 409. Для обеих операций поддерживается `Idempotency-Key`. Старые тела POST с `title`, `body`, `category` по-прежнему публикуются студентам и получают `sent`.
- Аудитория `all`, `students`, `employees` или `group` определяет доставку и чтение. Для `group` используется членство в учебной группе из справочника и обязателен `group_id`. После первой публикации аудитория фиксируется. Первая публикация создаёт адресные уведомления и запись истории в одной транзакции. Повторная публикация сохраняет первоначальную дату и историю и не создаёт повторных уведомлений. Уведомление из нового редактора содержит ссылку и заголовок. Чтение полного текста проверяет статус объявления и текущую аудиторию.
- Данные объявления хранятся в `campus_announcements`, редакционные снимки используют `workspace_operation_events`. При старте демонстрационной БД учебный офис получает три исходные публикации. История уже выданных уведомлений сохраняется. Редактор поддерживает немедленную публикацию и сохранение черновика.

## Глобальные уведомления

- `GET /api/notifications`, `GET /api/notifications/unread` и `GET /api/notifications/{id}` доступны всем авторизованным ролям. Сервер ограничивает выборку аккаунтом текущего сеанса. Список поддерживает категории `schedule`, `deadline`, `request`, `announcement`, `direct`, `academic`, `material`, `service`, `union`, `vuc` и фильтр `unread`. Сортировка по времени и ID идёт от новых записей к старым.
- `POST /api/notifications/{id}/read` и `POST /api/notifications/read-all` требуют подтверждения источника запроса и меняют состояние только своих уведомлений. Старый `/api/workspace/notices` возвращает совместимое представление того же списка.
- `POST /api/notifications/deadline-reminders` формирует напоминания о незавершённых заданиях на сегодня и ближайшие три дня с учётом настройки пользователя. Повтор того же события исключает уникальный ключ срока. Отправка личного сообщения и создание уведомления происходят в одной транзакции. Отметка диалога как прочитанного обновляет уведомления получателя до последнего увиденного сообщения.
