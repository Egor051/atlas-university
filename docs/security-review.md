# Проверка безопасности ATLAS Campus

Дата: 6 ноября 2026 года. Объект: локальный конкурсный прототип на FastAPI / SQLAlchemy и браузерный клиент. Все использованные учётные записи и записи в тестовой базе вымышлены. Реальные вузовские системы и персональные данные не использовались.

Проверку выполнял отдельный ИИ-агент роли Security reviewer в этой итерации. Это проверка кода и воспроизводимые регрессионные сценарии, а не независимый внешний аудит или аттестация информационной системы. Серверные исправления вносил агент Backend; интерфейс исправлял основной агент.

## Как повторить

Из корня проекта после установки `requirements-dev.txt`:

```powershell
.venv/Scripts/python.exe -m pytest -q tests/test_security.py
```

Модуль использует отдельную временную SQLite-базу. Файл рабочего демо `atlas.db` не изменяется. При запуске всего `tests/` используется временная база общего API-набора. В тесте перезапуска лимитера второй интерпретатор Python открывает ту же временную базу, поэтому результат не зависит от памяти первого процесса.

## Угрозы и доказательства

| Проверка | Воспроизведение | Требуемое поведение |
|---|---|---|
| Доступ без сеанса | GET личных API, включая документ, календарь и детали сотрудника | 401 и `Cache-Control: no-store` |
| Чужие данные через параметр | `?student_id=<ID другого студента>` у профиля, расписания, оценок, заявок, дедлайнов и уведомлений | Возвращаются только данные вошедшего студента |
| IDOR заявки и документа | Марк обращается по ID заявки Алины до и после готовности; также проверяется отсутствующий ID | Одинаковый 404; статус и владелец не раскрываются |
| IDOR уведомления | Алина отмечает уведомление Марка прочитанным и затем выполняет «прочитать все» | 404 на чужой ID; уведомления Марка не изменяются |
| IDOR дедлайна | Алина меняет `is_done` дедлайна Марка | 404; исходное значение сохраняется |
| Разделение ролей | Студент открывает/изменяет очередь сотрудника; сотрудник открывает студенческие данные | 403, включая новые маршруты документа и экспорта |
| Присвоение владельца и статуса | POST заявки с лишними `student_id`, `status` или `role` | 422; новая запись не создаётся |
| CSRF | POST без заголовка ATLAS, с чужим Origin, `Origin: null`, cross-site и чужим same-site источником | 403; корректный same-origin запрос проходит |
| Хранение паролей и сеансов | Проверка БД после входа | Argon2id-хеш пароля и SHA-256 токена; исходного токена в БД нет |
| Повтор сеанса после выхода | Сохранить cookie, выйти, повторно предъявить прежнюю cookie | 401; новый вход выдаёт другой токен |
| Истечение сеанса | Установить прошедший срок действия в тестовой БД | 401 для личных и служебных API |
| Дублирование заявки | Повтор POST с тем же Idempotency-Key, изменённым содержимым, затем ключ другого студента | Тот же ID для повтора; 409 при изменённом содержимом; отдельный ID другого владельца |
| Конкурирующая обработка | Две записи сотрудника на основе одной версии | Устаревшая версия получает 409 |
| Необъяснённое отклонение | Перевести заявку в rejected с пустым ответом | 422; состояние заявки сохраняется |
| XSS в документе | В комментарий и ответ вставить `<script>alert(1)</script>` | HTML экранирован; выполнение скриптов запрещено CSP; документ помечен как вымышленный |
| Перебор с разными именами | 40 неудачных входов одного IP, затем новая клиентская сессия и новый процесс | 429 и Retry-After, в том числе после перезапуска процесса |
| Перебор одного имени | 12 неудачных входов одной пары IP/логин | Следующая попытка получает 429 |
| Гонка лимитера | После 10 сбоев выполнить ещё 6 запросов параллельно | Только 2 получают 401, остальные 4 — 429 |
| Тело без Content-Length | Передать валидное JSON-тело больше 32 KiB потоковой загрузкой | 413 без доверия к одному заголовку размера |
| Небезопасный продакшен | Убрать Secure cookie / HTTPS origin; задать wildcard hosts или SQLite | Запуск с APP_ENV=production отклоняется |
| Отключение публичного демо | При уже существующих трёх тестовых аккаунтах переключить DEMO_MODE=false | Публичные логины получают 401; флаг отражается в публичной конфигурации |
| Обход production-проверок | Передать короткий пароль БД в URL-кодировке или APP_ENV с опечаткой | Пароль проверяется после декодирования; неизвестная среда отклоняется |

## Что исправлено по результатам ревью

1. **Проверка источника локальных запросов.** В исходной реализации сравнение Origin работало только при заданном PUBLIC_ORIGIN. Для воспроизведения использовался POST `/api/login` с правильным X-Requested-With и чужим Origin при отсутствии PUBLIC_ORIGIN. Теперь источник сверяется и с локальным адресом сервера; соседний сайт не считается доверенным источником.
2. **Ограничение перебора.** Исходная очередь в памяти имела ключ IP/логин, не давала общей квоты IP и исчезала при перезапуске процесса. Ошибки входа теперь учитываются в SQL; проверяются квоты IP и пары IP/логин. Проверка для отсутствующего пользователя также выполняет Argon2, чтобы не использовать мгновенный отказ как признак существования учётной записи.
3. **Строгие контракты.** Лишние поля, включая попытку назначить владельца, отклоняются валидатором. Владелец всегда назначается сервером. У `is_done` допускается только логическое значение JSON, а не строки или числа.
4. **История и конфликт записей.** Статус, ответ и событие истории сохраняются одной транзакцией. Версия записи предотвращает перезапись решения другого сотрудника. Причина отклонения обязательна.
5. **Безопасный результат заявки.** Документ выдаётся только владельцу готовой заявки, скачивается как вложение, экранирует введённый текст, запрещает скрипты и содержит явное предупреждение о конкурсном образце.
6. **Сеансы и эксплуатация.** Просроченные сеансы очищаются; ограничено число активных сеансов одной учётной записи. Валидация production-конфигурации требует HTTPS, Secure cookie, явного списка хостов и PostgreSQL. Публичные демонстрационные учётные записи несовместимы с production-базой при выключенном DEMO_MODE; проверяются как новый вход, так и ранее выданная cookie.
7. **Гонка лимитера.** Простое сохранение ошибок в SQL само по себе не предотвращало гонку «посчитать → проверить пароль → записать». Проверка и резервирование квоты сериализуются транзакционной блокировкой: SQLite BEGIN IMMEDIATE и PostgreSQL advisory lock по IP. Параллельная регрессия действительно выполняет шесть одновременных HTTP-запросов приложения.
8. **Ограничение тела запроса.** Вместо доверия Content-Length ограничиваются полученные ASGI-байты. Превышение 32 KiB возвращает 413 с теми же защитными заголовками и запретом кеширования.
9. **Защита от ошибки конфигурации.** Два дополнительных целевых теста воспроизвели обход проверки длины пароля БД через URL-кодировку (`%41` одиннадцать раз) и молчаливое переключение на development при опечатке APP_ENV. Исправление декодирует пароль перед проверкой и разрешает только известные значения среды. Повтор этих двух регрессий: **2 passed, 38 deselected**.

Исходный CSP запрещал `style=` в HTML, хотя клиент использовал такие атрибуты. Это реальное расхождение сервера и статического рендера; основной агент устранил inline-стили в интерфейсе. Проверка отсутствия CSP-ошибок выполняется в браузерных сценариях всей сборки.

## Отдельная проверка браузерных гонок и повторной отправки

При ревью нового клиента выявлены ветви, в которых запоздалый ответ прежнего пользователя мог обновить интерфейс уже нового пользователя, а ошибка доступа к sessionStorage после успешного POST могла выдать сохранённую заявку за неудачную отправку. Исправления основного агента: поколение сеанса для асинхронных запросов; безопасное удаление черновика; ключ повторной отправки в памяти формы; блокировка изменяемых полей во время сохранения. Время ожидания охватывает также чтение тела JSON, а не только получение HTTP-заголовков.

В `tests/test_frontend_contracts.py` три воспроизводимых Chromium-регрессии:

1. Задержать настоящий ответ навигатора Алины; выйти и войти Марком; доставить ответ. Ответ Алины не появляется у Марка.
2. Задержать запрос уведомлений Алины; выйти и войти Марком; выполнить прежний запрос с прежней cookie и доставить реальный 401. Новый интерфейс и сеанс Марка сохраняются.
3. Полностью запретить sessionStorage; после реального сохранения заявки оборвать ответ; повторить отправку. Оба POST используют один ключ; в БД остаётся одна заявка и открывается её история.

Самостоятельный запуск: **3 passed in 4.46s**. Использовались настоящий временный HTTP-сервер, отдельная SQLite-база и Chromium на ширине 1440 px. Данные API не подменялись: тесты только задерживали реальные ответы или обрывали ответ после фиксации транзакции. После тестов собственный сервер остановлен. Это не проверка мобильного устройства, публичного сайта или доступности из России.

```powershell
$env:ATLAS_RUN_BROWSER_TESTS='1'
.venv/Scripts/python.exe -m pytest -q tests/test_frontend_contracts.py
```

## Результат и границы доказательства

Самостоятельный запуск Security reviewer после серверных исправлений: **39 passed, 1 warning in 5.26s**. Команда: `.venv/Scripts/python.exe -m pytest -q tests/test_security.py`. Предупреждение — устаревающий alias BlockingPortal в зависимости Starlette/AnyIO; оно не связано с падением проверки. Пул SQLite закрывается в завершении тестового модуля, чтобы Windows мог удалить временную базу.

- В перечисленных негативных сценариях межстуденческое раскрытие данных, обход роли и изменение чужой записи не воспроизведены после исправлений. Для XSS проверены экранированный исходный HTML документа и запрет скриптов в CSP; API-тест не запускает JavaScript браузера. Это не доказательство отсутствия всех возможных уязвимостей.
- API-регрессии выполняются против настоящего приложения через ASGI TestClient. Это не проверка публичного сайта или соединения TLS.
- Процессный перезапуск и параллельный доступ лимитера проверяются на SQLite. Поведение PostgreSQL и контейнеров проверяется отдельным набором выпуска, если соответствующая среда доступна.
- Агент QA/Release дополнительно сообщил об успешном фактическом smoke-тесте PostgreSQL + HTTPS с проверкой локального CA, непривилегированной роли БД, IDOR, workflow, перезапуска и backup/restore в изолированном Docker Compose. Это отдельная проверка выпуска, а не выполненная Security reviewer проверка публичного домена. Инструкции: `docs/deployment.md`, `docs/operations.md`.
- Публичный домен, доступность из России, защита реальной инфраструктуры и независимый аудит не входят в результаты этих локальных тестов.
- Публичные пароли предназначены исключительно для фиктивного конкурсного демо. До подключения реальных данных нужны отдельная модель доступа и учётных записей, требования к хранению данных и внешняя проверка безопасности.

## Финальная интеграционная проверка основным агентом

После обновления FastAPI до 0.133.0 и Starlette до 1.3.1 общий набор прошёл: **68 passed**, включая три настоящие Chromium-регрессии. Тест повторной отправки расширен на закрытие/открытие формы при запрете sessionStorage: черновик и ключ остаются в памяти вкладки, сервер сохраняет одну заявку. Дополнительно исправлены обновление фильтра непрочитанных, фоновые focus-targets и гонка отложенного автофокуса; Tab/Escape проверены без смягчения утверждений.

Два предупреждения относятся к TestClient/httpx и alias Starlette/AnyIO; ошибки тестов отсутствуют. Точный вывод JUnit и хеши находятся в `verification/pytest-results.xml` и `verification/test-report.json`. Python-advisory проверены отдельным pip-audit по двум сервисам: [dependency-review](dependency-review.md). Этот финальный интеграционный проход выполнен основным агентом и не приписывается раннему самостоятельному запуску Security reviewer.
