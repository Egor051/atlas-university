# Подготовка эксплуатации и дополнительные проверки ATLAS

Итерация, начатая 8 ноября 2026. Эти инструкции относятся к текущему Python-приложению и подготовленным воспроизводимым проверкам. Датированные JSON-результаты показывают, что было действительно выполнено; наличие команды само по себе не означает успешную приёмку. Публичный домен, реальное российское подключение, физические устройства, оплата и будущая доступность не подменяются локальными проверками.

## Одна изолированная приёмка PostgreSQL и HTTPS

Включите Docker Engine и выполните из корня проекта:

```powershell
.venv/Scripts/python.exe scripts/improvement_deployment.py
```

Скрипт создаёт отдельное уникальное имя Compose-проекта, новые тома, закрытую сеть и локальный порт `https://localhost:19443`. Он сам генерирует временные пароли и не записывает их в JSON. Порт и подсеть `172.30.88.0/24` должны быть свободны. Существующая рабочая БД и чужие контейнеры не используются. По завершении контейнеры/сети только этого проекта останавливаются; новые тестовые тома сохраняются. Если порт занят, сначала выберите другой свободный порт в `compose.improvements.yaml` и скрипте; не останавливайте чужое приложение.

Проверяется фактическая сборка текущих исходников, валидный локальный сертификат Caddy с явно указанным доверенным CA, два web-процесса, вход трёх аккаунтов, изоляция, полный путь заявки и её результата, новые учебные/сервисные сущности, гонки за последнее место/экземпляр, перезапуск web+PostgreSQL. `pg_dump` восстанавливается в новую БД; число строк и digest отсортированного содержимого сравниваются для **всех** пользовательских таблиц. В отчёте нет самих личных строк или секретов.

Результат: `docs/verification/improvements-2026-11-08/postgres-https.json`. Это проверка локального TLS, а не внешнего ACME или российского маршрута. Исторический receipt версии 2 не заменяется этим файлом.

## Нагрузка, рост SQL и скорость интерфейса

```powershell
.venv/Scripts/python.exe scripts/improvement_sql.py
.venv/Scripts/python.exe scripts/improvement_load.py
.venv/Scripts/python.exe scripts/improvement_performance.py --runs 5
```

`improvement_sql.py` считает SELECT при малом и увеличенном наборе данных, сохраняя размер ответа и время. Это проверяет, растёт ли число запросов вместе с количеством строк. Профиль добавляет 40 курсов/160 модулей, 100 заданий и 100 тем. Принятый порог: не более baseline+3 запросов и не более 12 SELECT на запрос в выбранных списках.

`improvement_load.py` запускает настоящий HTTP-сервер с новой SQLite, добавляет 1000 вымышленных книг, 350 тем и по 100 конспектов двух студентов. Восемь клиентов выполняют 800 чтений десяти видов с паузой 5 мс. Сохраняются p50/p95/p99, пропускная способность, ответы и профиль среды. Принятый локальный порог: без неожиданных ответов, p95 ≤1000 мс. Такой результат не является обещанием вместимости публичного сервера.

`improvement_performance.py` открывает свежие браузерные контексты с выключенным кешем. Мобильная лабораторная модель: 390×844, задержка 150 мс, 1,6 Мбит/с вниз, 750 Кбит/с вверх, CPU×4. Отдельно измеряются первый экран входа, готовность личной главной после входа, переходы и CLS. LCP ≤2,5 с и CLS ≤0,1 используются как ориентиры. EventTiming публикуется только как лабораторная характеристика искусственных взаимодействий; **полевой INP и настоящие пользователи этим не измеряются**. Не меняйте бюджет после просмотра результата только ради PASS: сначала устраните причину либо явно пересогласуйте профиль.

## Другие браузеры и передаваемый архив

```powershell
.venv/Scripts/python.exe -m playwright install firefox webkit
.venv/Scripts/python.exe scripts/improvement_crossbrowser.py
.venv/Scripts/python.exe scripts/improvement_archive.py --archive dist/ФИНАЛЬНЫЙ-АРХИВ.zip
```

Cross-browser проверка проходит разделы на 360/390/1440 px и реальный UI-путь «создание заявки → сотрудник → результат → скачивание» в Firefox/WebKit. WebKit на Windows не является физическим iPhone или установленным Apple Safari; эти пункты остаются отдельной ручной приёмкой.

Проверка архива безопасно распаковывает именно передаваемый ZIP, создаёт **новое** Python-окружение, устанавливает runtime-зависимости с текущими constraints без обновления закреплённых версий, выполняет `pip check`, запускает извлечённое приложение на своей БД и проверяет путь заявки, IDOR и сохранение после нового процесса. Требуются сеть для установки пакетов и свободное место. Итог привязан к SHA-256 архива. После любого изменения приложения финальный архив и эту проверку нужно повторить.

## Мониторинг готового домена

```powershell
.venv/Scripts/python.exe scripts/improvement_monitor.py --url https://ВАШ-ДОМЕН --checks 60 --interval 60 --report monitor.json
```

Это только безопасное чтение readiness с обязательной проверкой сертификата. Желательно запускать наблюдение с внешней площадки. Отдельный запуск с реального подключения в РФ без VPN подтверждается датой, источником и фактическим результатом. Процент успешных выборок относится только к периоду измерения; он не доказывает отсутствие сбоев между выборками или доступность до будущей даты.

Перед отправкой работы владельцу нужны постоянный адрес, DNS и HTTPS, период размещения до 28 ноября включительно, уведомления от хостинга, ответственный за сбои, актуальный чистый исходный архив и доступные ссылки. Сценарий резервирования/восстановления — `docs/operations.md`; не храните единственную копию на том же сервере.

## Ограничение ресурсов и CI

Compose ограничивает web 512 МБ/128 процессов, PostgreSQL 512 МБ/128 процессов и Caddy 128 МБ/64 процесса; PostgreSQL/web не имеют внешних портов. Это начальные ограничения конкурсного стенда. Перед публичным запуском сопоставьте их с ресурсами VPS и измеренной нагрузкой. У приложения дополнительно остаётся предел соединений, а квоты прикладных записей не заменяются ограничением памяти контейнера.

В GitHub workflow подготовлены самостоятельные задачи PostgreSQL/TLS и расширенных измерений. Наличие workflow не свидетельствует о реальном удалённом запуске CI; для подтверждения нужна ссылка на успешный run соответствующей финальной версии.

## Размещение

Текущая архитектура рассчитана на Python, PostgreSQL и обычный reverse proxy; минимальный путь — VPS/контейнерный хостинг с существующими `compose.yaml`, `Dockerfile`, `deploy/Caddyfile`. Sites исполняет серверный JavaScript/Cloudflare Worker, поэтому размещение только статической оболочки не заменит работающие API и сохранение. Перенос на другую платформу допустим после проверки её Python runtime, постоянной БД, ограничений и собственных доменов. Не используйте БД другого проекта ради конкурсного стенда.

После выбора принадлежащего вам домена можно создать приватную конфигурацию без ручного придумывания паролей:

```powershell
.venv/Scripts/python.exe scripts/improvement_prepare_deploy.py --domain campus.example.ru
docker compose up -d --build --wait --wait-timeout 240
```

Первая команда откажется перезаписывать существующий `.env`, создаст разные криптографически случайные пароли и проверит Compose, не печатая их. На Linux файл получает режим 0600; на Windows необходимо также проверить локальные ACL каталога. Сам файл не передаётся жюри и не попадает в исходный архив. Домен в примере нужно заменить своим; его DNS должен указывать на выбранный сервер, TCP80/443 должны вести к Caddy. Закрытую БД не публикуйте отдельным внешним портом.

## Что остаётся ручным

Физические Android/iPhone, настоящий скринридер с участием пользователя, согласованные интервью и UX-тесты со студентами, оплата/владение доменом, российское подключение и капитанские ручные действия отмечаются только по фактическим свидетельствам. Автоматические сценарии и искусственные пользователи помогают находить ошибки, но не доказывают востребованность или понимание сервиса людьми.
