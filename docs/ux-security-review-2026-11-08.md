# Проверка безопасности при упрощении интерфейса

Дата: 8 ноября 2026 года. Область: локальный конкурсный прототип ATLAS Campus с вымышленными пользователями. Проверку выполнил отдельно назначенный агент Security reviewer; это проверка исходников и воспроизводимых сценариев, а не внешний аудит.

## Изменение контракта

По прямому запросу пользователя удалены модель `AssistantQuestion` и операция `POST /api/navigator`. Маршрут больше не зарегистрирован в приложении. Для гостя, обоих студентов и сотрудника обращение возвращает 404; персонального ответа нет. Удаление не затрагивает схему БД, вход, оценки, расписание, заявки, историю и уведомления. Миграция и очистка пользовательских записей не требуются.

Проверка удаления состоит из API-регрессии `test_removed_navigator_has_no_route_for_any_account` и браузерной регрессии `test_removed_assistant_is_absent_for_both_students_and_endpoint_is_unavailable`: проверяются отсутствие карточки/кнопок помощника, сетевых обращений клиента и недоступность серверной операции. Дополнительный тест `test_delayed_dashboard_response_never_replaces_new_student_data` сохраняет проверку запоздавшего успешного персонального ответа после смены аккаунта. Прочие проверки `sessionEpoch`, отложенного 401 и учебных диалогов сохранены.

## Фактически выполненная проверка API

Команда после удаления операции:

```powershell
.venv\Scripts\python.exe -m pytest -q tests/test_api.py tests/test_security.py tests/test_campus_security.py tests/test_learning.py tests/test_services.py
```

Результат: **91 passed**, 16,89 с; 2 предупреждения об устаревающих интерфейсах Starlette/httpx и AnyIO. Пропусков и ошибок нет. Сборки тестов создают временные SQLite-базы до импорта приложения; рабочая `atlas.db` не открывалась для записи этим запуском. Повторный запуск процессов в проверках сохранения использует эти же временные файлы.

| Угроза / сценарий | Проверяемый результат |
|---|---|
| Подстановка `student_id` в query профиля, оценок, расписания, сроков, заявок и уведомлений | Ответ остаётся данными студента из серверной сессии |
| Чужая заявка и скачивание документа на разных этапах | 404, как у несуществующего ID; владелец получает готовый документ |
| Чужое уведомление и массовое чтение | Чужой ID — 404; read-all меняет только собственные строки |
| Студент в `/api/staff/*` | 403 на чтение и запись |
| Сотрудник в студенческих API | 403, в том числе оценки, расписание и личные учебные данные |
| Присвоение `student_id`, `role` или готового статуса через тело заявки | 422, новая чужая запись не создаётся |
| Запись без заголовка, с чужим Origin, cross-site/same-site контекстом | 403; положительный same-origin путь работает |
| Повторная отправка заявки / конфликт payload | Тот же ключ и тело возвращают ту же заявку; другое тело — 409; ключи разных владельцев независимы |
| Недопустимый переход, гонка сотрудника, отклонение без причины | 409 или 422; состояние и версия остаются согласованными |
| Выход и истёкший сеанс | Прежний токен больше не авторизует запрос |
| Пароли и сессии | Argon2id; токен в БД только как хеш; HttpOnly/SameSite; секреты не отражаются в ошибках |
| Чужие курсы, работы, конспекты, карточки, попытки самопроверки, задачи и журнал времени | Owner-проверки и запрет массового присвоения владельца |
| Чужие диалоги, записи, регистрации, выдачи книг и финансы | Owner-проверки, ролевое разделение, запрет повторной отмены |
| Гонка за последним местом или экземпляром | Один победитель, второй получает 409; освобождение ровно один раз |
| Свой поиск и HTML-выгрузки | Поиск другого студента не находит чужую запись; HTML-строки экранируются; выгрузки с CSP sandbox |
| Опасные ссылки в работе/портфолио | Исполняемые схемы, credentials и управляющие символы отвергаются |
| Перезапуск приложения и повторное заполнение | Сохраняются пользовательские изменения, удаления, отправленные работы и записи |

В этих сценариях воспроизводимых нарушений IDOR, CSRF или ролевого разделения не обнаружено. Это результат указанных проверок, а не утверждение об отсутствии любых уязвимостей.

## Требования к обновлённому интерфейсу

- Брать владельца только из серверной сессии; фильтры и поиск не должны добавлять присылаемый браузером `student_id`.
- Не заменять `esc`/безопасный DOM-ввод сырыми пользовательскими строками. Это относится к названиям, текстам, атрибутам, формам редактирования, результатам поиска и сообщениям сотрудника.
- Сохранять проверку `sessionEpoch` в общем API-клиенте и проверку идентификатора открытого диалога. Старый ответ не должен появиться в новом аккаунте или заменить новый диалог.
- Сохранять CSRF-заголовок, идемпотентный ключ отправки и черновик, отдельный для аккаунта, включая случай запрета браузерного хранилища.
- Переходить из результатов поиска только в разрешённые разделы. Для ссылок на внешние проекты оставлять HTTPS и `noopener noreferrer`.
- Показывать, что данные вымышлены и сервис является конкурсным концептом, включая диалоги и скачанные образцы.

## Точное открытие результата поиска

При проверке UX найдено несоответствие сущности назначения: поиск возвращал ID оценки с `target=courses` и ID учебного срока с `target=assignments`. Совпадение названия не гарантирует совпадения ID курса, оценки и сдачи. Исправлено узко: оценки направляются в `grades`, сроки — в `plan`; возвращаемый ID относится к записи соответствующего списка. Заявки, уведомления, портфолио и конспекты сохраняют свои исходные назначения.

Для точного открытия уведомления добавлен `GET /api/notifications/{id}`. Он использует существующий сериализатор уведомлений: `{id,title,body,category,created_at,is_read,target,request_id}`. В SQL обязательны одновременно ID уведомления и ID студента из сессии. Гость получает 401, сотрудник — 403; чужой и отсутствующий ID дают одинаковые 404. Чтение не меняет `is_read`; для этого остаётся существующий защищённый POST. Схема и сохранённые данные не изменялись.

После этой правки выполнено:

```powershell
.venv\Scripts\python.exe -m pytest -q tests/test_search_contracts.py tests/test_api.py tests/test_security.py tests/test_campus_security.py
```

Результат: **58 passed**, 12,75 с, 2 прежних deprecation-предупреждения. Новый `tests/test_search_contracts.py` проверяет назначения и принадлежность ID обоих студентов, аутентификацию и роль, двусторонний IDOR, подстановку `student_id`, одинаковый ответ для чужого/отсутствующего ID и отсутствие изменения read-флагов при GET. Использована временная БД.

## Реальные браузерные проверки нового интерфейса

После обновления UI выполнено:

```powershell
$env:ATLAS_RUN_BROWSER_TESTS='1'
.venv\Scripts\python.exe -m pytest -q tests/test_frontend_contracts.py tests/test_extension_frontend_security.py tests/test_usability_security.py tests/test_search_contracts.py
```

Финальный результат после точных переходов и защиты диалогов: **17 passed**, 22,63 с; без пропусков, 2 прежних deprecation-предупреждения. Это 13 реальных браузерных сценариев и 4 API-контрактных теста. Использованы настоящий Chromium, локальный HTTP API и временная SQLite-база. В fault-injection сценариях задерживается полученный от сервера настоящий успешный ответ; успешные payload не подменяются.

Проверены:

- Отсутствие помощника, кнопок его вопросов и сетевых обращений для обоих студентов; `/api/navigator` возвращает 404.
- Поздний 401 старого аккаунта не завершает сеанс нового студента.
- Поздний успешный dashboard Алины не подменяет главную Марка.
- Повтор после потери уже сохранённого ответа создаёт одну заявку, даже если `sessionStorage` запрещён.
- Поздний результат самопроверки не открывается в другом аккаунте; закрытый старый диалог не заменяет подписи ответов нового.
- Пользовательская разметка в карточках конспектов, портфолио и редакторах остаётся текстом; ссылки портфолио имеют HTTPS и безопасный `rel`.
- Поздний настоящий `/api/campus/search` ответ Алины не появляется в открытом поиске Марка; серверный поиск Марка не возвращает её уникальную запись.
- Старый ответ поиска не заменяет результаты другой строки в том же диалоге и в повторно открытом диалоге.
- HTML/SVG/img-разметка в названии и тексте пользовательского конспекта остаётся буквальным текстом в общем поиске; внедрённых элементов нет, обработчики не выполняются. Нажатие открывает редактор именно этого конспекта с полными точными title/body и без внедрённого DOM.
- Выбранный результат конспекта при задержке загрузки его раздела не заменяет новый поиск, уже открытый пользователем.
- Открытие заявки из уведомления при задержке списка заявок не заменяет новый диалог поиска после получения старого ответа.

Последний сценарий сначала воспроизвёл реальный дефект: после загрузки списка заявок `openNotice` проверял лишь аккаунт и страницу, затем открывал карточку поверх уже нового поиска. Прогон до исправления: 16 passed / 1 failed. Исправление добавило проверку идентификаторов диалога и загрузки после `route('requests')`; итоговый прогон 17/17 подтвердил, что новый диалог сохраняется. Это гонка интерфейса внутри одного аккаунта, а не обнаруженная утечка чужих данных.

Изначальные два браузерных теста самопроверки потребовали адаптации навигации: перед кликом теперь раскрывается соответствующая группа бокового меню. Тест безопасного вывода конспекта использует текущие `.compact-row`/`.note-preview` вместо прежней карточки. Исходные проверки поздних ответов, точных строк и отсутствия внедрённых элементов сохранены; принудительных кликов по скрытым элементам нет.

## Границы

В этом отчёте зафиксированы завершённые API- и браузерные проверки безопасности. Общая проверка удобства, скриншоты, геометрия экранов и доступность публикуются отдельно в итоговой приёмке. Публичный адрес, TLS, доступность с российского подключения и физический телефон этим запуском не проверялись. Внешние службы и настоящие учётные данные не использовались.
